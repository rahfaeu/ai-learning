Boas práticas de IA no trabalho

IA no trabalho:
como usar sem terceirizar o cérebro

Uma sessão prática sobre LLMs, prompts, contexto, limites e senso crítico para usar IA com qualidade, velocidade e responsabilidade.

Abra com energia. Diga que a aula não é sobre “virar guru de IA”, mas sobre evitar o uso tosco: copiar, colar e torcer. A promessa é simples: sair sabendo usar IA como par técnico.

Use esta frase como âncora. A aula inteira volta para ela: IA aumenta a capacidade de quem sabe formular, validar e decidir.

Fundamento 1
8–11 min
O que é uma LLM?

Uma máquina de predição de linguagem

Ela recebe um contexto e calcula qual continuação é mais provável, útil ou coerente com a instrução.

Contexto → Probabilidades → Próximo token → Resposta
Cuidado com “ela sabe”. Diga: ela não sabe como uma pessoa; ela modela padrões de linguagem. É muito poderosa, mas não é garantia de verdade.
05
Fundamento 2
11–14 min

LLM não lê texto como gente.
Ela lê tokens.

Texto humano

Criar uma tabela incremental no dbt.

Visão aproximada do modelo

[Criar] [ uma] [ tabela] [ incremental] [ no] [ db] [t] [.]

Tudo vira pedaço.

Prompt, arquivos, histórico, documentação e resposta competem pelo mesmo orçamento de tokens.

Diga que token é a moeda de atenção. Tudo que entra consome espaço. Arquivo gigante “só por garantia” é como levar mudança inteira para uma reunião de 30 min.
06
Fundamento 3
14–17 min

Transformer: o modelo usa atenção para conectar partes do contexto

1. Lê pedaços

O texto é dividido em tokens.

2. Pesa relações

O mecanismo de atenção estima quais partes importam mais.

3. Gera continuação

A resposta nasce token por token, com base nessas relações.

Atenção é como vários marca-textos trabalhando ao mesmo tempo.
Não aprofunde matemática. A turma só precisa entender que “atenção” não é consciência: é um mecanismo para ponderar relações no texto.
Referência: Attention Is All You Need07
Fundamento 4
17–21 min

SQL calcula.
LLM interpreta intenção.

Determinístico

SELECT 2 + 2;

-- Resultado: 4

Mesma entrada, mesmo resultado.

Probabilístico

Explique dbt para uma pessoa iniciante.

-- Pode gerar várias boas respostas.

Mesma entrada, resposta pode variar.

Aqui nasce a necessidade de validação. Se a ferramenta é probabilística, não dá para tratar output como verdade determinística.
08
Prompt Engineering
21–24 min

Prompt bom não é bonito.
É operacional.

Fraco 
Melhore esse código.
Forte 
Revise este modelo dbt para Databricks.
Avalie:
1. materialização
2. chave incremental
3. risco de merge duplicado
4. legibilidade
5. aderência ao padrão

Não reescreva ainda. Primeiro liste os problemas.
Mostre que o segundo prompt reduz ambiguidade, define papel, critérios e ordem. O segredo é pedir análise antes de artefato.
09
Context Engineering
24–27 min

Melhor que perguntar bonito é dar o contexto certo.

  • 1Qual é o objetivo?
  • 2Qual contexto é realmente necessário?
  • 3Quais restrições e padrões devem ser respeitados?
  • 4Qual formato de saída eu quero?
  • 5Como vou validar?
Diga: context engineering é curadoria. O profissional bom não joga tudo na IA; ele prepara um briefing limpo.
10
Harness Engineering
27–29 min

Harness é a estrutura que coloca a IA para trabalhar com controle.

prompt base arquivos skills MCPs guardrails testes evals logs critérios de aceite
Prompt é o pedido.
Contexto é a mochila.
Harness é o cinto de segurança.
Explique que o curso não precisa se aprofundar no termo. O importante é a ideia: IA profissional precisa de estrutura, não só conversa solta.
11
Context Window
29–32 min

Janela de contexto não é memória perfeita.
É uma mesa de trabalho.

O que entra?

  • prompt e histórico
  • arquivos e documentação
  • código, erros e logs
  • skills, MCPs e tools
  • respostas anteriores

Por que reduzir?

  • menos ruído
  • menos conflito
  • menos custo
  • menos alucinação
  • mais foco no problema
Use a analogia da mesa. Mesa grande ajuda, mas se estiver cheia de papel velho, o trabalho piora. Contexto menor e relevante vence contexto gigante e bagunçado.
12
Quando a janela fica grande
32–35 min

Três nomes úteis para quando o contexto começa a dar ruim

Context overflow

Passou do limite. Parte do conteúdo é cortada ou a chamada falha.

“Não coube na cabeça do modelo.”

Lost in the middle

A informação está lá, mas o modelo ignora ou usa mal o miolo do contexto.

“Coube, mas se perdeu no meio.”

Context rot

A qualidade degrada conforme o contexto cresce, mesmo antes de bater o limite.

“Mesa maior, bagunça maior.”

Esta é a resposta para a pergunta do termo. Não existe um único nome oficial. Use os três e explique a diferença.
Termos: context overflow, lost in the middle, context rot13
Prática recomendada
35–37 min

Uma conversa por objetivo.
Um contexto por problema.

Evite 
Na mesma conversa:
- arquitetura
- bug de SQL
- mensagem para stakeholder
- documentação
- decisão técnica
- desabafo existencial
Prefira 
Conversa 1: entender problema
Conversa 2: desenhar solução
Conversa 3: revisar código
Conversa 4: escrever documentação
Conversa 5: preparar comunicação
Brinque com o desabafo existencial, mas volte ao ponto: histórico acumulado vira ruído. Separar contexto aumenta qualidade.
14
Vibe coding vs desenvolvimento assistido
37–40 min

Vibe coding é acelerar sem volante.

Desenvolvimento assistido por IA é acelerar com direção, freio, teste e checklist.

Não é o foco
  • copiar SaaS em 20 minutos
  • aceitar código sem ler
  • gerar tela bonita sem arquitetura
  • trocar engenharia por tentativa e erro
É o foco
  • melhorar qualidade com velocidade
  • reduzir trabalho repetitivo
  • revisar riscos e alternativas
  • documentar, testar e validar melhor
Aqui você alinha expectativa do curso. Não é anti-velocidade. É pró-velocidade responsável.
15
Fluxo recomendado
40–42 min

Use IA como par técnico, não como piloto automático.

  • 1Explique o problema e o objetivo.
  • 2Forneça só o contexto necessário.
  • 3Peça crítica antes de pedir solução.
  • 4Compare alternativas e trade-offs.
  • 5Valide com teste, documentação e revisão humana.
Reforce: pedir crítica antes de código é uma das maiores mudanças de qualidade. A IA fica muito melhor quando trabalha como revisora antes de trabalhar como geradora.
16
Limitações
42–44 min

A IA pode errar com muita convicção.

Alucinação

Inventa função, fonte, comando, coluna ou explicação plausível.

Desatualização

Pode não conhecer mudanças recentes ou detalhes internos.

Sensibilidade

Pequenas mudanças no prompt podem mudar muito a resposta.

A IA não fica vermelha quando chuta.
Esta frase gruda. Use para reforçar que confiança no tom não é evidência. Tom seguro não é teste unitário.
17
Senso crítico
44–46 min

O risco não é a IA escrever.
O risco é você parar de avaliar.

Risco de cadeia

Modelos são construídos sobre disputas reais: dados, autoria, trabalho intelectual, copyright e poder computacional.

Exemplo para debate: Project Panama, da Anthropic, citado em documentos judiciais e reportagens sobre escaneamento destrutivo de livros.

Risco cognitivo

Delegar demais enfraquece a habilidade de formular problema, revisar solução e defender decisão técnica.

Use IA para aprender mais rápido, não para pensar menos.

Não transforme em sermão. O ponto é maturidade. Use IA, mas entenda que há custos, riscos e responsabilidades.
18
Fechamento
Fechamento
Use IA para acelerar o trabalho.
Não use IA para abandonar o pensamento.Leia. Questione. Valide. Edite. Assuma.
Feche com a frase e pare. Não explique demais. O fechamento precisa soar como regra de bolso.

Template de prompt profissional

Você é meu par técnico para revisar uma solução.

Objetivo:
[descreva o resultado esperado]

Contexto:
[cole apenas o necessário]

Restrições:
[tecnologia, padrões, riscos, convenções]

Tarefa:
Primeiro critique a solução.
Depois proponha melhorias.
Não gere código ainda.

Critérios de avaliação:
- clareza
- simplicidade
- aderência ao padrão
- riscos técnicos
- manutenibilidade
